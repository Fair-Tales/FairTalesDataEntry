**Privacy is an admission requirement, with two source policies.** The former universal requirement to manually approve every batch is replaced for the chosen exclusive capture source; retaining it would defeat the owner’s decision.

1. **Forward source authorization:** one-time setup authorizes a specific owner/device, exclusive book-camera output directory and immutable source policy, not arbitrary files in a folder with a reassuring name. Personal shooting remains in stock-camera `DCIM/Camera`; the sync rule never watches that directory, Google Photos, all of Pictures, or new folders discovered automatically. Restrict the sync app’s local folder access where supported (**UNVERIFIED** Android grant behavior). A synthetic personal-camera photo must not appear in any transfer. The selected book camera must not also save a personal-roll copy for syncing, mix its destination with personal captures, or silently fall back to `DCIM/Camera` on lost folder access. Those failures stop automation.
2. **Legacy or mixed sources:** before any image, thumbnail, original filename, EXIF metadata, image-level classifier result or source record reaches research S3/Firestore, show a private local contact sheet and obtain explicit approval of the exact ordered book/separator manifest. Download permission, classifier permission and research-admission permission are separate. A date range or surrounding separators do not establish book-only content. Personal files stay on the owner’s machine/source account and never enter staging as a means of filtering them later.
3. **No silent personal-photo admission:** source segregation is the forward prevention mechanism; no classifier is required. Any detected misfiled, uncertain, corrupt or ambiguous item holds the affected run for confirmation; never auto-delete it or concatenate around a gap. An accidentally personal shot taken inside the dedicated book app cannot be infallibly recognized by a folder rule. The no-personal-transfer guarantee relies on keeping that app exclusively for books, as the owner chose; it is not a claim that a folder name detects content. Do not silently ingest a known or suspected personal photograph. If this invariant fails, pause that device and use the incident procedure below.
4. The optional Haiku classifier is **OFF and non-load-bearing for the forward path**. It proposes inclusion/exclusion for an explicitly opted-in safety review; it never authorizes personal material or auto-accepts uncertainty. For mixed legacy days, local human review is preferable because sending a personal thumbnail to Anthropic is still exposure. Classifier-OFF means zero classifier calls and costs, not permission to skip legacy admission. No automatic model escalation.
5. Strip GPS and unnecessary device metadata from upload copies while preserving full resolution and correct orientation. Keep original bytes on the phone/private local machine and bind original and sanitized digests. For direct sync this must happen **on the phone before the watched upload folder**, or be established by the camera’s output configuration; generic sync is not a metadata scrubber. Disable location recording in the book camera and verify resulting files. If the camera cannot produce compliant copies, an automatic local preparation component is required; its availability/integration is **UNVERIFIED** and is a release gate, not an assumed feature of FolderSync. It can read an exclusive capture directory and atomically publish sanitized files to an exclusive outbox; it must not scan the personal roll. Preserve only needed ordering evidence in a minimal manifest.
6. Personal photographs never enter the research data store. The S3 landing prefix is an isolated **book-only transport inbox**, not personal-photo quarantine. No rejected-image collection in Firestore. No candidate images, original filenames, tokens, signed URLs, personal OCR text or free-form model descriptions in telemetry. Use opaque IDs and aggregate counters. Local previews do not use cloud thumbnails or persistent browser/service-worker caches; revoke object URLs when finished. Any optional transient classifier path needs disclosed authorization and verified no-spool/no-log behavior.
7. Nothing automatically deletes phone, Photos, Drive or private legacy originals. Uncertain items remain available for confirmation. The separately specified expiry of verified transport copies never authorizes deletion of originals or unreviewed uncertain content. Maintain the existing incident inventory/removal procedure for a mistaken admission.

The server waits for every listed object and verifies its bytes even if the marker arrives first. No new terminal black shot is required or presumed.

Producing that inventory requires a reliable session boundary on the phone. Investigate a capture-session wrapper or camera integration that closes the inventory as part of the already accepted switch out of book capture, preserving all completed saves and rejecting interrupted writes. **Open Camera lifecycle hooks, FolderSync/Autosync completion hooks, and One UI support for this are UNVERIFIED.** An app-background event, screen lock or timeout by itself cannot prove the owner finished shooting. An adapter feeds **60/60/60/20 internal chunks without four user selections**; uses the shared allocator/checkpoints, source staging and freeze checks; runs the existing splitter; then invokes the existing confirmation/binding path only for unambiguous, complete, non-overlapping book groups within quota. **Phone credential and staging isolation — first-class release gate.** Never copy or reuse the application’s AWS keys from `.streamlit/secrets.toml`; that file is not read for this design. Provision a dedicated IAM principal per owner/device, with a separately revocable credential for the sync app and no shared app/admin policies. Proposed landing path uses existing excluded top-level `uploads/`: `S3_BUCKET/uploads/phone_books/<owner_id>/<device_id>/`. Keys below it include opaque session/item IDs. Resolve `S3_BUCKET` through [s3_constants.py](../s3_constants.py), not a second hard-coded bucket constant. The current `NON_BOOK_S3_PREFIXES` already excludes `uploads` and `batch_sources` from orphan-book discovery.

The phone’s effective permission is **only `s3:PutObject` on `arn:aws:s3:::<S3_BUCKET>/uploads/phone_books/<owner_id>/<device_id>/*`**. No `s3:GetObject`/`GetObjectVersion` (including HEAD-based object reads), `DeleteObject`/`DeleteObjectVersion`, `ListBucket`, bucket-wide discovery, ACL/tag/policy changes, research-prefix access, or access to another device’s prefix. Enforce the allow-list with a permissions boundary and bucket-policy review so another grant cannot expand it; explicitly deny object read/delete and all writes outside this prefix. No console access or other AWS-service credentials. TLS, block-public-access, private object ownership and encryption at rest are required configuration checks. Current IAM/bucket/KMS configuration is **UNVERIFIED**; if customer-managed encryption needs extra KMS actions, security design must be reviewed rather than silently broadening this write-only contract.

**Test the sync app with those exact rights.** Many sync designs compare remote files with LIST/HEAD; whether either candidate supports pure push without those calls is **UNVERIFIED**. Start with single-object PUTs for the expected photo sizes. Multipart listing/abort permissions, if required by a client, are not assumed; incomplete multipart cleanup belongs to the server lifecycle. If strict write-only operation fails, the product fails F1 qualification. Do not grant object read, bucket list, delete or application credentials to make the demo work; qualify a compatible push mode or F2 instead. Store the dedicated key using the sync app’s protected credential storage if available (**UNVERIFIED**); avoid clipboard history, screenshots, logs and ordinary device backups containing the key. Short-lived credentials are preferable only if the app can refresh them automatically with equally narrow authority (**UNVERIFIED**); otherwise acknowledge the revocable long-lived device-key risk.

A prefix in the same bucket is a logical isolation boundary, not a separate security domain. Research pages, `batch_sources/`, worker artifacts and Firestore remain inaccessible to the phone. Only the gated, authenticated server adapter can promote a verified source into the durable research pipeline via shared helpers. Listing/reconstruction/UI paths must exclude the landing prefix, and server access to it is bounded to registered owner/device sessions. The backend must validate that keys, owner/device, manifest and gate match; data inside an uploaded file cannot expand authority. A stolen phone credential can write bogus inbox objects even though it cannot read research data. Reject invalid manifests, enforce size/count/budget limits, and stop a device with abnormal arrivals. Do not treat the path alone as evidence of an authenticated owner instruction.

`PutObject` can overwrite an existing key even without delete rights. Use unique session/item keys, pin expected byte digests and object versions when supported, and verify the exact copy accepted into `batch_sources/`; changed bytes invalidate the revision. If immutability controls/versioning are used, qualify their compatibility and cost (**UNVERIFIED** deployment support). Never let later inbox overwrites replace frozen sources or update existing books. The phone is never given permission to modify durable copies.

**Lifecycle:** propose an S3 rule scoped to the exact phone staging prefix **and a server-controlled `retention=transport_expirable` tag**, expiring eligible objects after **30 days from object creation**. This includes verified book-only arrivals that are **never ingested**, not just successful batches. Separately abort incomplete multipart uploads after **7 days**, leaving phone originals intact. These are proposed retention durations; the exact tag/version rule behavior is **UNVERIFIED** until configuration testing. Never place either rule on the bucket root, `batch_sources/` or research books.

All arriving complete objects start **on hold by default**, without the expiry tag. Only the retention controller, never the phone, may mark a transport copy expirable after checking its registered exclusive source, manifest/digest and a retained recoverable original, with no unresolved uncertainty. Successful research ingestion is not required for eligibility: a complete verified session waiting for an importer or abandoned before admission can still expire. Uninspected, corrupt, missing-manifest or uncertain items remain held, are surfaced for confirmation, and are **never automatically deleted**. This explicit exception takes precedence over bounded storage; a stalled controller must leave extra storage, not erase unresolved material. Notify on stale held arrivals and abnormal byte counts, pause further device uploads if necessary, and obtain an explicit disposition for items that cannot be cleared. The landing area is not an intentional repository for personal photos; a known personal arrival invokes the incident procedure instead of routine retention tagging.

Before normal expiry, warn at days 21 and 28 and stop presenting missing objects as resumable. Expiry is object-age based, not a fresh 30-day clock when a tag is added: an old held item cannot be released into immediate deletion without explicit review and a recovery interval. If an already eligible run becomes uncertain, revoke expiry eligibility and verify the hold; if imminent deletion/protection cannot be ruled out, verify a separately protected copy outside the expiry scope before proceeding and suspend the affected expiry policy. Do not claim an asynchronous rule change cancels an already queued deletion. Preserve the phone/private source throughout. With versioning, protect every unresolved version; enable noncurrent-version expiry only after proving that holds cover those versions as well. Hold/recovery maintenance must remain available when research admission is OFF, without starting ingestion or paid classification. Test importer outage, failed tagging, revocation, late uncertainty and gate-OFF recovery before lifecycle is enabled. Originals and uncertain evidence have no automatic-delete policy.

**Lost phone:** immediately deactivate the dedicated access key/principal authorization, suspend that device’s importer and outstanding promotion leases, and hold arrivals from the suspected compromise interval for review. If temporary credentials are used, verify revocation/expiry coverage; do not assume disabling an issuer kills every existing session. Check bounded device-prefix request logs and unexpected objects without logging image content. Remove unauthorized arrivals through the incident procedure; assess any already promoted batch. Enrol a replacement device with a new principal/key after configuration verification. Existing application keys are neither installed on the phone nor rotated as a substitute for revoking the device. Revocation and a synthetic attempted write/read outside scope are qualification exercises for a later authorized pilot, not actions taken now.

**Retained R2 analysis: phone-browser multi-select — DISQUALIFIED.** The current HTML requests `accept="image/*" multiple`; actual Galaxy picker limits/codecs/cloud-only retrieval are **UNVERIFIED**. Eliminating albums does not eliminate the rejected selection burden.

The code gives a definite answer about 200 photos:

- `MAX_UPLOAD_PAGES = 60`; the strict browser handler rejects a larger selection before any image PUT (`photo_upload.py`, lines 54, 990–998, 1065). A single 200-photo selection **does not upload**. Four selections, `60 + 60 + 60 + 20`, fit within the 1,200-photo batch limit. The separate allocation limit is 100 chunks (lines 771–772). These are application limits, not Android limits.
- Today each selection requires selecting files, waiting, “Finish this selection,” checking progress, then “Add another selection” or “Finish batch.” Four selections mean four picker visits and four Finish-selection actions, three Add-selection actions and one Finish-batch action, plus progress checks and book review. - Per-image limit is `50 × 1024 × 1024` bytes, **50 MiB**, despite the UI's “50 MB” wording. No total-byte cap was found. The mathematical allowance for 200 files is `200 × 50 MiB = 10,000 MiB ≈ 9.77 GiB`; that is not a realistic-size estimate or evidence that a phone can handle it.

Existing `bind_book` prevents duplicate creation for the **same group**, but suffixes an existing title for a new group. Job source identity hashes ordered S3 keys, not page content (`background_pipeline.create_or_get_job`). Therefore a new batch containing the same photos can currently create another Book. A title match is not sufficient deduplication either.

Proposed identity rules:

- Resume uses the same batch ID, manifest revision, chunk/slot and verified upload digest. Names and sizes alone are insufficient; current resume compares those, so add hash verification before reuse. A lost acknowledgement retries the same slot, never appends a new position.
- For admitted nonseparator photos, use stable source ID plus version where available, and exact original SHA-256 independent of route. Store the sanitized-upload digest separately and verify server-side. Provider URLs and file names are not identity. Separator bytes never reserve a book-content identity; many black frames can legitimately be identical.
- Before creating a new book, lookup exact-content claims and an ordered group fingerprint containing the ordered original photo hashes, preserving sequence and multiplicity. An occurrence is its ordinal in this canonical sequence, not a newly minted batch-specific ID; otherwise reimport would change the fingerprint. A canonical exact-group claim is independent of classifier/pipeline version so upgrading processing cannot invent another Book. Freeze those versions as processing provenance instead.
- Extend the existing book-binding transaction to claim the group fingerprint atomically with book creation/group binding. A competing batch with the same group must point to the existing book/job or show a recoverable conflict; it must not win a different suffixed title. Per-source reservations and deterministic manifests detect partial overlap, subsets and reordered copies. Bounded reservations are checkpointed before binding rather than assuming one transaction can fit an arbitrarily large book. Each reservation is atomically create-or-fail with an immutable owner/batch/token; attachment uses a matching version precondition. Conflicts remain blocked/resumable, never automatically expired or stolen based on cached state. Administrative release requires checking the original batch and revoking its approval before reuse. Any additional transactional ownership revalidation/reclamation reads must be charged explicitly.
- Any overlap with an already admitted photo, including a partial batch or changed order, stops new-book creation for review. Offer “resume/open existing book” or an explicit intentional reuse/append workflow with provenance. Do not silently drop the overlap and create a second truncated book. The default is no duplicate book. A deliberate repeated endpaper gets a distinct approved occurrence in the same book.
- Cloud re-encoding, cropped exports and independently reshot pages defeat exact-byte identity. Stable source-version checks and, optionally, locally calculated normalized/perceptual similarity can flag candidates; similarity is never grounds for automatic deletion/merging. If identity cannot be established, require review. Do not promise detection of every reshot copy.

Only exact duplicate/overlap decisions use indexes; do not scan every Book/Page collection or run the entire S3 audit per batch. Claims are scoped by owner/access policy to avoid exposing another researcher's content. Any broader project deduplication needs an explicit permission model.
